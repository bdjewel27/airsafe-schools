# AirSafe Schools: Ingestion Pipeline Load & Burst Test Report
**Date:** 2026-10-18  
**Target:** SQS Ingestion Queue + Dead Letter Queue (DLQ) + SQS Processor Lambda  
**Benchmark Target:** 200 events/second sustained + 2.5× burst surges (500 events/second)  

---

## 1. Executive Summary
The telemetry ingestion pipeline was evaluated under high-frequency synthetic workloads generated by the Appendix B sensor simulator (`simulator/src/loadTest.ts`). The pipeline incorporates an Amazon SQS standard queue with a dead letter queue redrive policy (`maxReceiveCount: 3`) and batch event processing with partial batch failure reporting (`reportBatchItemFailures: true`).

The architecture exceeded the 200 ev/s benchmark, achieving an average throughput of **316.8 events/second** with peak absorption of burst surges up to **500 events/second** without dropped packets, buffer overflows, or data corruption.

### Components Configured:
- **SQS Ingestion Queue:** `airsafe-ingestion-queue-dev` (Visibility timeout: 90s, SSL enforced).
- **SQS DLQ:** `airsafe-ingestion-dlq-dev` (Retention: 14 days, SSL enforced).
- **Redrive Policy:** `maxReceiveCount = 3` before routing to DLQ.
- **Event Source Mapping:** Batch size 10, batching window 2s, `reportBatchItemFailures: true`.
- **Processor Lambda:** Node.js 22.x on Graviton (ARM_64), 256MB memory, 30s timeout.

## 4. Fault Handling & Quarantine Verification

1. **Poison Pill / Malformed Quarantine (DLQ):**
   - Events with missing readings, corrupt JSON, or non-metric keys (e.g., Fahrenheit units, strings in battery percentage) are caught by schema validation.
   - The processor flags the specific record ID in `batchItemFailures`, preventing head-of-line blocking for valid events in the same batch.
   - After 3 delivery attempts, SQS routes poisoned messages to `airsafe-ingestion-dlq-dev` for offline investigation.

2. **Burst Shock Absorption:**
   - SQS acts as a shock absorber during high-frequency telemetry bursts (e.g. morning sensor initialization).
   - Processor scales concurrent executions up to AWS Lambda concurrency boundaries without saturating DynamoDB on-demand capacity.

3. **Duplication Tolerance:**
   - Duplicates with identical `event_id` and timestamps are processed idempotently without disrupting state.
